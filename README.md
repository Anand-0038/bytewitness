# ByteWitness

ByteWitness creates portable, self-signed file integrity receipts entirely in the browser. A file is hashed in chunks with SHA-256, the receipt is signed with a non-exportable ECDSA P-256 device key, and the resulting JSON proof can be verified later with no account, upload, or server.

[Try ByteWitness](https://bytewitness.regal-flame-7335.chatgpt.site) · [Devpost project](https://devpost.com/software/bytewitness)

![ByteWitness seal flow](public/screenshots/bytewitness-desktop.png)

## Why it exists

Students, creators, journalists, and freelancers often need a simple way to show that a file they shared later is byte-for-byte identical to the one they sealed. Existing timestamp and blockchain products can add stronger third-party time guarantees, but they also add infrastructure, cost, and trust dependencies. ByteWitness is the small, private baseline: deterministic file-integrity and receipt-signature verification that works offline after the app loads.

## Judge demo

1. Open ByteWitness and seal a small file.
2. Download the `.bytewitness.json` proof.
3. Verify the original file with that proof: the result confirms a file match and a valid ECDSA signature.
4. Change one character in the original file and verify again: ByteWitness reports a file mismatch.
5. Edit any signed field in the JSON receipt and verify again: ByteWitness rejects the signature.

The whole flow is visible in the browser network panel: no file or hash is sent anywhere.

For a fast walkthrough, choose **Try the guided sample** in the seal flow. It loads a harmless
browser-local sample, lets you create a real receipt, and walks through changed-file and
tampered-receipt verification using the same verification path as any other file. After a
verification result, **Download verification report** exports a plain-text summary with the
result, digests, signer key ID, and trust boundary.

## Security model

ByteWitness proves:

- the checked file has the same SHA-256 fingerprint recorded in the receipt;
- the receipt fields have not changed since they were signed;
- the receipt was signed by the private key corresponding to its included public key;
- receipts created in the same browser profile normally share the same device key ID.

ByteWitness does **not** independently prove a person's identity, legal ownership, or a trusted external creation time. The displayed time comes from the user's device clock. A malicious person can create their own key and receipt. For authorship claims, publish or exchange the displayed key ID through an independently trusted channel.

During verification, an optional **Expected signer key ID** can be supplied from that independently trusted
channel. ByteWitness then reports three separate outcomes: receipt integrity, file integrity, and whether the
receipt key matches the expected signer. An empty expected-signer field intentionally remains **not established**;
the receipt's included public key cannot identify its owner by itself.

The seal result includes **Copy key ID** so the signer can exchange that fingerprint through a trusted channel
before a handoff. Copying is best-effort and falls back to manual selection when browser clipboard access is
unavailable.

The private signing key is generated by Web Crypto as non-exportable and stored in IndexedDB when the browser allows it. Clearing site data or ending a private-browsing session may remove the signing key, but existing receipts remain verifiable because they include the public key. Hardened environments may fall back to a session-only key and show that state explicitly.

## Local development

Requirements: Node.js 22+ and npm 10+.

```bash
npm install
npm run dev
```

Run the complete local release gate:

```bash
npm run check
```

## Architecture

- React 19 + Vite 6 static web application
- TypeScript with strict checking
- Web Crypto ECDSA P-256 signatures
- Incremental SHA-256 hashing with `@noble/hashes` in 2 MB chunks
- Zod validation for untrusted proof receipts
- IndexedDB for the non-exportable browser signing key
- Optional expected-signer key ID comparison for trusted handoffs
- No backend, analytics, accounts, cookies, or network API

## Proof format

Proofs are readable JSON and use format `bytewitness-proof`, version `1`. The signature covers the format version, client-clock time, exact file metadata and SHA-256 fingerprint, signing algorithm, key ID, and public key. Verification rejects unknown fields and unsupported versions.

## Privacy

ByteWitness processes original files entirely on the device. The deployed static app does not receive the file, fingerprint, receipt, or key. Font files and icons are bundled with the application rather than loaded from third parties.
